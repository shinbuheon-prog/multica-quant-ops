# 펀더멘털 파이프라인 × multica-quant-ops 통합 설계 (초안)

*작성일 2026-09-03 · 최종 개정 2026-09-03 (실행 착수 중 발견 사실 2건 반영) · 상태: 실행 중*

> 이 문서는 코드를 옮기기 전에 먼저 검토받기 위한 설계 메모였고, 이제 실행 단계입니다.
> 8절은 결정 사항 로그, 9절은 **저장소를 실제로 열어보고 발견한, 기존 6개 결정을
> 다시 확인해야 하는 사실 2가지**입니다.

## 0. 결론 먼저

지금 하는 걸 요약하면: **두 시스템을 합칩니다.** 하나를 버리고 하나를 새로 짓는 게 아닙니다.

- Cowork 세션에서 8월부터 키운 **펀더멘털 채점 파이프라인**(46단계, 44개 정식 채점
  종목·SEC 원문 대조·건전성등급·투자점수)은 **분석 엔진**입니다. 문제는 이게 사는 곳 —
  세션이 끝나면 통째로 사라지는 컨테이너 — 입니다.
- 4월에 이틀간 만들고 4.5개월 방치된 **`multica-quant-ops`**는 겉보기엔 참고용 폴더였지만
  실제로 열어보니 **에이전트 오케스트레이션·안전정책·감사로그·리포팅까지 갖춘, 테스트
  90개가 통과하는 실제 작동 프레임워크**입니다. 문제는 이게 비어 있다는 것 — 담을 분석
  내용이 없습니다.

한쪽은 내용은 있는데 집이 없고, 한쪽은 집은 있는데 내용이 없습니다. 이 문서는 펀더멘털
파이프라인을 `multica-quant-ops`의 구조 안으로 옮기고, 그 결과로 생기는 상시 실행 위치에
투자 전담 에이전트 여러 개를 붙이는 설계입니다.

## 1. 현재 두 시스템 비교

| | Cowork 펀더멘털 파이프라인 | multica-quant-ops |
|---|---|---|
| 정체 | 46단계 스크립트 파이프라인 (`run_pipeline.sh`) | 에이전트 오케스트레이션 패키지 (Python, pytest 90개 통과) |
| 강점 | SEC 원문 대조·항등식 검증·건전성등급·투자점수·대시보드, 4개월간 실전 검증됨 | task/agent 상태머신, 안전정책(킬스위치·시장시간 게이트), 감사로그, 스케줄러, 리포팅 골격 |
| 약점 | **집이 없음** — 세션 컨테이너 휘발성, 버전관리 없음(`build_ops_dash.py`의 무음 치환 버그가 여러 세션 동안 안 걸린 게 그 증거) | **내용이 없음** — 데이터 품질 체크는 OHLCV 가격 스냅샷 수준뿐, 펀더멘털 이상탐지·항등식 검증·등급 산출 로직이 없음 |
| 데이터 소스 | SEC EDGAR 원문 + XBRL 교차검증 + IR 자료, Alpha Vantage(가격) | Alpha Vantage 어댑터만 존재(`data/providers/alphavantage.py`), 쿼터 이 세션에서 이미 소진 확인됨 |
| 실행 방식 | 사람이 세션을 열 때만 실행, 최근 스케줄 트리거 실험 시작(공시 감지) | `scheduler.py`로 상시 스케줄 실행 전제 |
| 매매 실행 | 없음 (분석·모니터링 전용) | paper-trading 실행기 존재하지만 **라이브 실행은 코드 레벨에서 하드 차단**(`ValueError`) |
| 검증 문화 | "지어내지 않는다" — 수치는 ≥2개 독립 출처, 안 되면 공란 처리 | 코드 레벨 안전정책(테스트로 강제) |

**핵심 발견**: 두 시스템은 경쟁하지 않고 정확히 겹치지 않는 두 층을 맡고 있습니다.
`multica-quant-ops`가 이미 짜둔 5개 에이전트 역할(Research/Data/Signal/Backtest/Ops)은
제가 이번 대화에서 독립적으로 제안했던 역할 구성과 거의 그대로 수렴합니다 — 즉 처음부터
설계할 필요가 없고, **기존 골격에 지금 있는 로직을 이식**하면 됩니다.

## 3. 에이전트 재정의

기존 5개 역할을 폐기하지 않고 **확장**합니다.

| 기존 역할 | 재정의 | 담당 |
|---|---|---|
| `ResearchAgent` | **Scout** — 신규 종목 발굴, SEC/IR/공시 리서치, PDF 정독. LLM 세션이 담당 | 발굴은 자동 |
| `DataAgent` | **Sentinel** — 데이터 신선도(기존) + **펀더멘털 크기 이상탐지**(신규, GOOGL 건이 계기) + SEC 접수번호 워터마크 감시 | 자동 |
| `SignalAgent` | 그대로 — 궁극적으로 `factors_panel.csv` 소비 | 자동 (결정론적) |
| `BacktestAgent` | 그대로, 단 **6절의 lookahead 금지 규칙**을 코드 레벨로 강제 | 자동 (결정론적) |
| `OpsAgent` | 한국어 리포팅·대시보드export·주간 요약·공시 알림 흡수 | 자동 |
| *(신규)* | **Doctor** — 파이프라인 자체의 건강 진단. `verify_pipeline.py`류의 정합성 체크, 무음 실패 탐지(`build_ops_dash.py` 버그가 실제 계기), 스케일 체크 | 자동 |
| *(신규, 사람 개입점)* | **편입 승인** — Scout가 발굴한 종목을 "정식 채점 44종목"에 넣을지는 **사람 승인 후에만** 기존 검증된 파이프라인이 자동 실행 | **사람** |

이 표의 마지막 줄이 앞서 합의한 경계선입니다: **발굴은 자동, 편입 결정은 사람.** 승인이
떨어지면 그 다음(신규 종목 편입 절차, `자동감지_구조설계.md` 7-b절에 이미 실전 검증된
순서 — CIK 역추적 → 원문 판독 → XBRL 교차검증 → 6단계 파이프라인 → 워치리스트 등록)은
자동입니다.

## 4. 결정론적 에이전트 vs LLM 리서치 에이전트 — 반드시 지킬 경계

`multica-quant-ops`의 기존 엔지니어링 규칙("strategy code must be testable without
network access")과 이전 세션에서 확립한 **파라메트릭 선견편향(lookahead bias)** 원칙을
합치면 이렇게 정리됩니다.

- **결정론적 파이썬 에이전트** (Sentinel의 신선도 체크, Signal/Backtest의 팩터 계산,
  Doctor의 정합성 체크): 네트워크·LLM 의존 없이 테스트 가능해야 하고, `scheduler.py`로
  상시 실행됩니다. 입력은 이미 검증되어 저장된 CSV/JSON뿐입니다.
- **LLM 리서치 스텝** (Scout의 SEC/IR 정독, 신규 종목 발굴, 컨퍼런스콜 뉘앙스 파악):
  Cowork 세션 또는 Workflow 도구로만 실행 가능합니다 — 순수 Python 스크립트가 아닙니다.
  산출물은 **구조화된 파일**(JSON/CSV/MD)로 남기고, 그 이후는 결정론적 파이프라인이
  소비·검증합니다.
- **하드 룰 (`_github_agents.md`에서 이월)**: LLM은 **과거 특정 시점의 백테스트 판단에
  절대 쓰지 않습니다.** 모델 가중치 자체가 이미 그 이후의 실제 결과를 알고 있어서,
  "이 시점에 이 뉴스를 어떻게 해석했을까"를 LLM에게 물으면 답이 미래 지식으로 오염됩니다.
  이건 `known_date` 같은 파일 레벨 감사로는 못 잡습니다. → `backtest/engine.py`는 순수
  규칙 기반 팩터만 쓰고, LLM 판단이 들어간 신호는 백테스트 대상에서 제외합니다.

## 5. 데이터·실행 환경

### 5-1. 데이터 소스별로 경로를 분리합니다 (결정됨)

`자동감지_구조설계.md`(2026-08-28 실측)에서 이미 검증된 사실을 그대로 이월합니다:
**이 환경에서는 bash·python으로 URL을 직접 가져오는 게 정책상 막혀 있습니다**
(`requests`/`curl`/`wget` 전부 차단, 우회 불가). 웹 조회는 반드시 에이전트가 세션 안에서
`WebFetch`/`WebSearch` 도구로 직접 해야 합니다.

두 성격의 데이터를 하나의 방식으로 묶으려 한 게 애초에 무리였습니다. 나눠서 갑니다.

**펀더멘털 리서치(SEC 원문·IR·컨퍼런스콜)는 (B) 유지 — LLM 에이전트 직접 조회.**
항등식 대조·문맥 판단이 필요한 영역이라 애초에 Python 스크립트로 대체할 수 없고, 4개월간
검증된 방식이기도 합니다. 이 부분은 건드리지 않습니다.

**가격 데이터(OHLCV, Alpha Vantage)는 (A) GitHub Actions로 이전 — 권장안.** 이유:

1. **성격이 다릅니다.** 가격은 판단이 필요 없는 순수 숫자 시계열입니다. LLM 에이전트가
   `WebFetch`로 하나씩 조회하는 건 이 작업엔 안 맞는 도구를 쓰는 것 — 느리고, 세션
   시간을 쓰고, 쿼터가 소진되면(지금처럼) 그냥 멈춥니다.
2. **Cowork 세션 네트워크 정책과 정면으로 안 맞습니다.** `alphavantage.py`는 Python이
   직접 HTTP 호출을 하는 구조라, 이 세션 안에서 스케줄 작업으로 돌리면 애초에 막힙니다.
   GitHub Actions는 이 세션과 무관한 별도 실행 환경이라 이 제약 자체가 없습니다.
3. **6번 결정(가격 최신화 공백)을 구조적으로 해결합니다** — 아래 5-4절.
4. **비용이 안 듭니다.** GitHub Actions는 public 저장소 기준 무료이고, `ALPHAVANTAGE_API_KEY`는
   저장소 Secrets에 넣으면 됩니다(기존 PowerShell 스크립트의 `$env:ALPHAVANTAGE_API_KEY`
   관례와 동일선상). `data/providers/base.py`의 기존 어댑터 인터페이스를 그대로 씁니다 —
   새로 설계할 게 아니라 실행 위치만 옮기는 일입니다.

**주의할 점**: Alpha Vantage 무료 티어는 분당·일당 호출 제한이 있습니다. 60종목을 매일
갱신하면 한도에 걸릴 가능성이 있으므로, 워크플로 설계 시 (a) 요청 간 딜레이를 두거나
(b) 백업 소스(`_github_agents.md`에서 이미 후보로 검토된 stockanalysis.com 등)를 두는
걸 마이그레이션 단계(Phase 5)에 포함시키길 권합니다. 정확한 무료 티어 한도는 구현 직전에
다시 확인이 필요합니다 — 지금 확정 짓기엔 정보가 부족합니다.

### 5-2. 상태 저장 — 이미 실전 검증된 패턴 재사용

같은 문서에서 확인된 3개 벽(에이전트 밖 네트워크 불가 / 컨테이너 휘발성 / 금융 콘텐츠는
메모리 파일시스템 저장 차단)의 결론은 **"스케줄 작업이 실행될 때마다 자기 자신의
프롬프트를 다음 실행용으로 고쳐 쓴다"** 였습니다. 이건 이미 공시 감지 트리거에 구현되어
9월 7일 첫 실전 테스트(PANW Q4 FY26)를 앞두고 있는, **검증 대기 중이지만 이미 동작하는
선례**입니다.

이번 통합에서는 이 패턴을 GitHub과 결합합니다: 트리거 프롬프트의 워터마크 표는 실행
사이 상태(어디까지 봤는지)를 담고, **실제 산출물(리포트·CSV·점수)은 매 실행 끝에 GitHub
저장소에 커밋·푸시**해서 세션이 사라져도 결과는 남게 합니다. 즉:

```
스케줄 작업 실행 (매번 새 세션)
  → git clone (또는 이미 있으면 pull)
  → 워터마크 표로 "새로 볼 게 있는지" 판단
  → 있으면: 리서치(WebFetch) → 결정론적 검증 → 결과를 저장소에 커밋 → push
  → update_trigger로 워터마크만 갱신한 프롬프트 재작성
```

로컬 소재가 자연스러움).

다만 **가용성 제약을 분명히 해야 합니다**: 이 폴더는 Claude 데스크탑 앱이 그 컴퓨터에서
켜져 있고 이 세션에 연결돼 있을 때만 읽힙니다 — 지금 이 세션도 연결 안 된 상태입니다.
따라서 Scout 에이전트의 소스로 넣되 **"있으면 참고, 없으면 SEC/IR만으로 진행"** 형태의
보조 소스로 설계해야지, 스케줄 작업이 매번 이 폴더에 의존하게 만들면 안 됩니다(데스크탑이
꺼져 있는 밤 시간대 실행이 실패하게 됨 — 미국 실적 발표가 한국 밤 시간대에 몰리는 것과
정면으로 충돌).

**결정: 필요할 때만 연결(on-demand)을 권장합니다.** 상시 연결은 사용자가 그 컴퓨터에서
데스크탑 앱을 계속 띄워둬야 하는 부담을 지우는데, 그렇게 얻는 이득(로컬 PDF를 1차 소스로
승격)은 크지 않습니다 — 어차피 SEC/IR 원문이 1차 소스이고 로컬 PDF는 보완재일 뿐입니다.
자동화(스케줄 작업)는 항상 SEC/IR만으로 완결되게 설계하고, 로컬 폴더는 **심층 리서치가
필요한 순간**(편입 승인 검토, 분기 심층분석, 엑셀 모델 대조)에 사용자가 데스크탑 앱을
열어 그때만 연결하는 방식이 자동화 안정성과 사용자 부담 사이에서 더 낫습니다.

### 5-4. 가격 데이터 최신화 공백 — 구조로 해결

기존 44종목 중 29종목의 가격이 8/28 이후 갱신 안 된 문제는 임시 조치(예: 수동 재수집)를
따로 두지 않습니다. **원인 자체가 "가격 갱신이 Cowork 세션이 열릴 때만 일어난다"는
구조적 결함**이므로, 5-1절의 GitHub Actions 이전이 완료되면 이 공백은 정의상 사라집니다
— Cowork 세션 실행 여부와 무관하게 매일 정해진 시각에 60종목 전체가 갱신되기 때문입니다.
Phase 5(저장소 되살리기)에 이 워크플로 구축을 포함시켜, **임시방편 없이 최종 구조로 바로
가는 쪽**을 택합니다. 마이그레이션이 끝나기 전까지는 공백이 남아 있다는 점은 그대로
인지하고 있되, 그걸 메우려고 별도 스크립트를 만드는 건 나중에 버릴 코드를 만드는
일이라 하지 않습니다.

### 9-2. GAS 대시보드가 이미 있는데, 지금 실제로 쓰시는 것과 다릅니다 — 확인 필요

`docs/GAS_DASHBOARD.md`·`docs/CODEX_TEAM_DASHBOARD_DESIGN.md`를 보면 이 저장소에는
**이미 완성된 별도의 Google Sheets 대시보드**가 있습니다. 구조는:

```
Python(dashboard_export.py) → dashboard-export.json → Google Drive(수동 업로드) →
Apps Script(gas/quant_ops_dashboard/Code.gs) → 시트(Overview/Dashboard/Batch Runs/
Incidents/Config)
```

문제는 이게 **지금 실제로 매일 보고 계신 Cowork의 「지표 시트」·「통합대시보드」와 완전히
다른 시트**라는 점입니다. Cowork 쪽은 `sheet_export.csv`를 Apps Script가 직접 읽는 CSV
기반이고, 이쪽은 JSON을 Google Drive에 올리는 파일 기반입니다. 4월에 이 저장소를 만들 때
설계는 됐지만 (`CODEX_TEAM_DASHBOARD_DESIGN.md`에 "Codex가 로컬에서 실행" 전제가 깔려
있는 걸 보면) 실제 시트에 연결해 쓰신 흔적은 없어 보입니다 — 그 뒤로 Cowork에서 완전히
독립적으로 지금 쓰시는 대시보드를 만드신 것 같습니다.

**두 개를 나란히 유지하면 운영자가 두 화면을 봐야 하는, 자동감지_구조설계.md에서 이미

### 9-3. Alpha Vantage 무료 티어가 60종목 매일 갱신 용량에 못 미칩니다

`docs/ALPHAVANTAGE_FREE_MODE.md`: 이 저장소는 이미 파일 기반 일일 호출 카운터와 한도

점입니다 — **60종목을 매일 갱신하려면 하루 60콜 이상 필요한데, 무료 한도 25콜로는 애초에
안 됩니다.** 5-1절에서 제안한 GitHub Actions 이전은 이 가드 자체를 우회하는 게 아니라
"어디서 도는가"만 바꾸는 것이라, 이 용량 문제와는 별개로 여전히 풀어야 합니다.
`ALPHAVANTAGE_FREE_MODE.md`의 "업그레이드 시점" 기준("scheduler 자동화가 일상적으로
돌 것", "다종목 모니터링이 필요할 것") 두 개가 이번 통합으로 정확히 충족되지만, **결정은
유료 전환이 아니라 가격 전용 다른 무료 소스로 교체**입니다. Alpha Vantage는
`data/providers/alphavantage.py` 그대로 남겨두되(같은-날 준비(same-day prep)류 저빈도
흐름에서는 계속 씀), **일일 60종목 가격 갱신은 새 `data/providers/stooq.py`**로 분리합니다.

**소스 선정: Stooq.** 이유 — API 키 불필요(가입조차 불필요), 일별 OHLCV CSV를
`stooq.com/q/d/l/?s=<티커>.us&i=d` 형태로 직접 받을 수 있어 순수 HTTP GET 하나로 끝나고,
호출 한도가 사실상 종목당 1회·무료이며(공식 문서화된 유료 한도 없음, 다만 과도한 동시
요청은 자제), `_github_agents.md`에서 이미 후보로 검토됐던 stockanalysis.com 계열보다
CSV 파싱이 훨씬 단순합니다(HTML 스크레이핑이 아니라 진짜 CSV). 다만 Stooq는 SLA가 없는
무료 서비스이므로 **재시도 로직과 실패 시 이전 값 유지(하루 갱신 실패해도 파이프라인이
죽지 않게)**를 Phase 5 구현에 반드시 포함합니다.

### 9-4. Phase 6 착수 — 채점 로직 재작성 대신 "얇은 어댑터"로 방향 수정

Phase 6에 착수하며 `score5_full.py`~`score8_full.py`(4개, 총 1,900여 줄)와
`pipeline/s0_universe.py`~`s7_backtest.py`(12개 층, 약 4,000여 줄)의 실제 내용을 읽었습니다.
두 가지가 확인됐습니다:

1. **규모가 8절 결정 당시 가정보다 훨씬 큽니다.** 합쳐서 약 6,000줄이고, 그 상당 부분이
   숫자 계산이 아니라 **44종목 각각의 손리서치 판단 근거**입니다 — 예: `s0_universe.py`의
   섹터 재분류(ATI·AVAV를 "전력"에서 "항공우주·방위"로 옮긴 이유, 매출 비중 실측치까지),
   IPO/상장일 처리(SPCX·CRCL), 생존편향 계량화 로직, 20-F 외국민간발행인 예외처리(MUFG) 등.
2. **이 로직은 이미 자체 회귀 테스트를 가지고 있습니다** — Cowork 파이프라인 자신의
   `verify_pipeline.py`가 매 실행마다 286개 항목을 검사합니다(2026-09-03 기준 0 NG).

**결정 수정**: 이 채점 로직을 `multica-quant-ops`에 두 번째로 재작성하지 않습니다. 대신
`src/multica_quant_ops/fundamentals/`는 Cowork 파이프라인이 이미 내놓는 산출물
(`universe.csv`·`sheet_export.csv`)을 **유일한 소스**로 취급하는 타입 로더 +
파일간 정합성 검사 계층으로 구현했습니다:

- `fundamentals/universe.py` — `universe.csv` 타입 로더. `UniverseEntry`,
  생존편향-안전 `as_of(date)` 조회, `survivorship_gap_days()`(감시 시작 전 가격 이력
  일수)를 `s0_universe.py`의 4절 로직과 동일한 의미로 재현하되, 종목별 판단 근거 자체는
  재작성하지 않고 CSV를 그대로 신뢰합니다.
- `fundamentals/snapshot.py` — `sheet_export.csv`(지표 시트와 동일한 산출물) 타입 로더.
  한글 헤더 → 영문 필드명 매핑을 명시적으로 고정해, 헤더가 바뀌면 조용히 잘못 매핑되는
  대신 `SnapshotFormatError`로 즉시 실패합니다.
- `fundamentals/consistency.py` — 두 파일 사이의 정합성(모든 채점 종목이 유니버스에도
  있는가, 섹터가 일치하는가)과 필드별 값 범위(투자점수 0~10, 신뢰도 0~1,
  건전성등급/판정/매력도가 온톨로지.md에 정의된 값 중 하나인가)를 검사합니다. 이 계층이
  잡는 건 "동기화가 깨졌다"는 신호뿐입니다 — 점수 자체가 맞는지는 여전히 Cowork
  파이프라인과 사람의 몫입니다.

**남은 운영 질문(향후 Phase에서 결정)**: `universe.csv`·`sheet_export.csv`가 물리적으로
어떻게 이 저장소에 들어오는지는 아직 정하지 않았습니다. 현재는 Cowork 세션에서 수동으로
내보내 커밋하는 방식을 가정합니다 — 자동화(예: Cowork 세션 종료 시 export, 또는 별도
스케줄)는 Phase 8(공시 감지 GitHub 결합)과 함께 다룰 만한 별개 결정입니다.

### 9-6. `refresh-daily-prices.yml`을 GitHub Actions에서 처음 수동 실행하자 조용히 아무것도 커밋 안 하는 버그가 나왔습니다

Discord/Telegram 알림 배선을 확인한 뒤, 가격 갱신 워크플로우도 같은 방식으로 처음
수동 실행(`workflow_dispatch`)해봤습니다. 실행 자체는 초록 체크로 39초 만에 성공했는데,
`ops/prices/daily_prices.csv`가 저장소에 전혀 생기지 않았습니다 — 워크플로우가 실패한
게 아니라, **커밋 단계가 스스로 "변경 없음"으로 잘못 판단하고 조용히 건너뛴 것**이었습니다.

원인은 커밋 단계의 조건문이었습니다.

```bash
if git diff --quiet -- ops/prices/daily_prices.csv; then
  echo "No price changes to commit."
  exit 0
fi
git add ops/prices/daily_prices.csv
```

`git diff`는 **이미 추적 중인 파일의 변경 여부만** 비교합니다. 이번이 이 파일의 첫 실행이라
`ops/prices/daily_prices.csv`는 아직 git이 한 번도 커밋한 적 없는 미추적(untracked) 파일이고,
`git diff`는 미추적 파일을 아예 비교 대상에 넣지 않습니다. 그 결과 "차이 없음"으로 판정되어
`exit 0`으로 조용히 끝나버렸고, 뒤에 있는 `git add`/`git commit`/`git push`는 실행조차 안 됐습니다.
9-5절의 섹터 라벨 버그와 같은 성격입니다 — 합성 테스트나 실행 로그의 "성공" 표시만으로는
안 잡히고, 실제로 GitHub Actions에서 한 번 돌려서 저장소에 파일이 실제로 생겼는지 눈으로
확인해야만 드러나는 종류의 문제였습니다.

`git add`로 먼저 스테이징한 뒤 `git diff --cached --quiet`로 스테이징된 변경분을 비교하도록
고쳤습니다 — 이 방식은 신규 파일과 기존 파일 수정 양쪽 다 정확히 감지합니다. 저장소 안의
다른 워크플로우들은 이 패턴을 안 썼는지 확인했고(`grep -rn "git diff --quiet" .github/workflows/`),
이 파일 하나뿐이었습니다.
